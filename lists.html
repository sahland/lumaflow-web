Guide / Virtualized lists

Keep the data large. Keep the mounted tree small.

ListView<T> maps to UI Toolkit's native virtualized ListView, mounting widget rows only for the visible and recycle range.

Use when

Rows can growProjects, messages, search results and other scrollable collections.

2000 projects: search, sorting and selection.

Start from the first tutorial. Add the file below and using LumaFlowDocs.NextSteps; to AppRoot. Replace CounterPage with new ProjectListDemo() inside the existing Scaffold. Keep Bootstrap, Theme and Mount unchanged.

This local example creates 2000 mock projects in memory. It does not fetch server data or persist edits to disk. Project IDs remain stable across sorting and are not reused after deletion.

ProjectListDemo.cs · complete file
using System;
using System.Collections.Generic;
using System.Linq;
using LumaFlow;

namespace LumaFlowDocs.NextSteps {
    public sealed class ProjectListDemo : StatefulWidget<ProjectListDemoState> { }

    public sealed class ProjectListDemoState : WidgetState {
        private readonly List<Project> _all = new();
        private readonly State<string> _query = new("");
        private readonly State<IReadOnlyList<Project>> _visible = new(Array.Empty<Project>());
        private readonly State<IReadOnlyList<WidgetKey>> _selected = new(Array.Empty<WidgetKey>());
        private readonly State<string> _order = new("Ascending");
        private readonly ListViewController _scroll = new();
        private bool _descending;
        private int _nextId = 2001;

        protected override void InitState() {
            for (var id = 1; id <= 2000; id++) _all.Add(new Project(id));
            Refresh();
        }

        public override Widget Build(BuildContext context) => SizedBox.Expand(new Padding(
            new Column(new Widget[] {
                new Text("Projects", context.Theme!.Typography.Title),
                new TextField(_query, label: "Search", onChanged: _ => Refresh()),
                new Row(new Widget[] {
                    new Button("Reverse order", ReverseOrder),
                    new Button("Clear search", ClearSearch)
                }, gap: 8f),
                new Row(new Widget[] {
                    new Button("Add project", AddProject),
                    new Button("Delete selected", DeleteSelected)
                }, gap: 8f),
                new ReactiveBuilder<string>(_order, value => new Text(value)),
                new ReactiveBuilder<IReadOnlyList<Project>>(_visible, rows => new Text(
                    rows.Count == 0 ? "No matches. Clear the search." : $"Matches: {rows.Count}")),
                new ReactiveBuilder<IReadOnlyList<WidgetKey>>(_selected, keys => new Text(
                    keys.Count == 0 ? "Selected: none" : $"Selected: {keys[0].Value}")),
                new Expanded(new ListView<Project>(_visible,
                    project => new Padding(new Text(project.Name), EdgeInsets.All(8f)),
                    itemHeight: 44f,
                    itemKey: KeyOf,
                    selectionMode: ListSelectionMode.Single,
                    selectedKeys: _selected,
                    controller: _scroll))
            }, gap: 12f), EdgeInsets.All(24f)));

        private void Refresh() {
            var term = _query.Value.Trim();
            var matches = _all.Where(p => p.Name.IndexOf(term, StringComparison.OrdinalIgnoreCase) >= 0);
            _visible.Value = (_descending ? matches.OrderByDescending(p => p.Id) : matches.OrderBy(p => p.Id)).ToArray();
            _scroll.JumpTo(0f);
        }

        private void ReverseOrder() {
            _descending = !_descending;
            _order.Value = _descending ? "Descending" : "Ascending";
            Refresh();
        }

        private void ClearSearch() {
            _query.Value = "";
            Refresh(); // Programmatic assignment does not replay TextField.onChanged.
        }

        private void AddProject() {
            _all.Add(new Project(_nextId++));
            Refresh();
        }

        private void DeleteSelected() {
            var keys = new HashSet<WidgetKey>(_selected.Value);
            _all.RemoveAll(p => keys.Contains(KeyOf(p)));
            _selected.Value = Array.Empty<WidgetKey>();
            Refresh();
        }

        private static WidgetKey KeyOf(Project project) => new($"project:{project.Id}");

        private sealed class Project {
            public Project(int id) { Id = id; Name = $"Project {id:D4}"; }
            public int Id { get; }
            public string Name { get; }
        }
    }
}

Try the workflow

  1. Expect Matches: 2000 and the first projects. Scroll down: the list must not stretch the whole page.
  2. Select Project 0001. The summary becomes Selected: project:1.
  3. Press Reverse order. Selection follows the ID, not its old index.
  4. Search for “2000”: one result remains. Search for “zzz”: expect No matches. Clear the search.
  5. Press Clear search. All rows return. Assigning _query in code does not replay onChanged, so this action explicitly calls Refresh.
  6. With an empty query, Add project produces Matches: 2001. Select a row and Delete selected: that project is removed and selection clears.

Data, results and selection are different things

List data owners
FieldPurpose
_allThe full model collection. An ordinary List, not an observable collection.
_visibleA new filtered/sorted snapshot observed by ListView.
_selectedThe selected model's WidgetKey, not an index or native row reference.
_scrollA retained controller attached to one list.

Refresh uses ToArray and assigns a new snapshot to State. _all.Add(...) alone cannot notify it. Do not remount the application or reassign the same collection instance as a workaround.

What virtualization actually saves

ListView does not mount 2000 row trees at once: UI Toolkit reuses visible rows and a small buffer. The models and snapshot still occupy memory; filtering/sorting still process data. This is not server pagination or constant-time updating.

The example uses a 44-unit fixed row with short single-line text and 8-unit padding. For descriptions, larger text scaling or multiline cards, omit itemHeight to use dynamic height. Do not declare 44 units while drawing a 100-unit card.

A key is identity, not storage.

itemKey associates a model with a realized row during updates. Use a unique stable ID, not its index, editable name or a fresh Guid each Build. Virtualization can release rows; keep important drafts, checked flags and progress externally by ID rather than relying solely on row WidgetState.

Why selection survives a filter

This example intentionally retains _selected when filtering hides its model. Clearing the search reveals it again. Delete selected removes that model even when the filter hides it. This is an application policy. If selection should only cover current results, explicitly prune missing keys during Refresh.

Scrolling and bounded height

ListView already owns scrolling; do not wrap it in another vertical ScrollView. Scaffold supplies height, SizedBox.Expand fills it, Column reserves header space and Expanded gives the remainder to the list. Read the layout walkthrough.

Refresh intentionally jumps to the start. To preserve position, remove JumpTo(0) and define your filtering policy. ScrollTo accepts an item's key and returns false when the item is absent from current results or the controller is detached.

Common failures

  • Changed List but no UI update: assign a new State snapshot.
  • Sorting selects another project: retain its ID/key, not selectedIndex.
  • Collapsed or empty list: check bounded viewport height and Expanded, rather than guessing a larger itemHeight.
  • Row input vanishes after scrolling: store important values externally by ID.
  • Slow large-data search: virtualization does not accelerate filtering. Consider debounce, indexing or server search; cancel stale responses.

The row builder runs again during recycling. Return a UI description; do not start network requests, play sounds or create long-lived controllers inside it.

Next: open project details and return to the list.

The complete runnable example is above. The following API fragments use application-specific names such as ProjectRow, not built-in package classes.

Start with a typed row builder.

Use a fixed item height for uniform rows. Omitting it selects native dynamic-height virtualization.

ProjectsList.cs
new ListView<Project>(
  projects,
  project => new ProjectRow(project),
  itemHeight: 56f);

Key rows that carry state.

Give every row a deterministic, unique key when it owns focus, subscriptions or local state. A key follows a compatible realized row through insertion and reordering.

ProjectsList.cs
new ListView<Project>(
  projects,
  project => new ProjectRow(project),
  itemHeight: 56f,
  itemKey: project => new WidgetKey(project.Id));
Do not mutate a collection in place.

For reactive replacement, pass State<IReadOnlyList<T>> and replace its complete value. A mutable collection cannot notify the list by itself.

Keep selection outside the list.

Selection is controlled and key-based. User interaction commits the state before the callback runs, while programmatic changes update native selection without replaying the callback.

ProjectsList.cs
var selected = new State<IReadOnlyList<WidgetKey>>(
  Array.Empty<WidgetKey>());

new ListView<Project>(
  projects, BuildRow,
  itemKey: project => new WidgetKey(project.Id),
  selectionMode: ListSelectionMode.Multiple,
  selectedKeys: selected);

Retain a controller when scroll position matters.

Keep the controller at the same ownership boundary as the list configuration. It restores the offset after the native list has its geometry.

ProjectsList.cs
private readonly ListViewController _projectsController = new();

_projectsController.JumpTo(320f);
_projectsController.ScrollTo(new WidgetKey(projectId));
