Guide / Navigation and overlays

Keep routes and temporary UI under explicit ownership.

A Navigator retains application history. An OverlayController owns dialogs, drawers, popovers and toasts above that content.

Rule

Create controllers outside BuildOne controller belongs to one matching mounted host.

A working flow: list → details → back.

Add LocalCounter.cs from the local state lesson and the file below. In AppRoot, import LumaFlowDocs.NextSteps and replace CounterPage with new NavigationDemo() inside Scaffold. Keep Bootstrap, Theme and Mount unchanged.

NavigationDemo.cs · complete file
#nullable enable
using System;
using LumaFlow;

namespace LumaFlowDocs.NextSteps {
    public sealed class NavigationDemo : StatefulWidget<NavigationDemoState> { }

    public sealed class NavigationDemoState : WidgetState {
        private Navigator _navigator = null!;
        private readonly OverlayController _overlay = new();

        protected override void InitState() {
            _navigator = new Navigator(new HomePage(OpenDetails));
        }

        private void OpenDetails() => _navigator.Push(new Route(
            new WidgetKey("project-1"),
            new DetailsPage(() => { _navigator.Pop(); }),
            RouteTransition.Fade(TimeSpan.FromMilliseconds(180))));

        public override Widget Build(BuildContext context) => new BackNavigation(
            new OverlayHost(new NavigatorHost(_navigator), _overlay),
            _navigator, _overlay);

        private sealed class HomePage : StatelessWidget {
            private readonly Action _open;
            public HomePage(Action open) => _open = open;
            public override Widget Build(BuildContext context) => new Padding(
                new Column(new Widget[] {
                    new Text("Project list"),
                    new LocalCounter(),
                    new Button("Open project 1", _open)
                }, gap: 16f), EdgeInsets.All(24f));
        }

        private sealed class DetailsPage : StatelessWidget {
            private readonly Action _back;
            public DetailsPage(Action back) => _back = back;
            public override Widget Build(BuildContext context) => new Padding(
                new Column(new Widget[] {
                    new Text("Project 1 details"),
                    new Button("Back to projects", _back)
                }, gap: 16f), EdgeInsets.All(24f));
        }
    }
}

What to test

  1. On Project list, press Increment local count three times.
  2. Press Open project 1: Project 1 details appears.
  3. Press Back to projects: the list returns with Local count: 3.
  4. Repeat: the stack contains the list and current details, not duplicate home screens.

Why the count survives: Push retains the previous mounted route but makes it inactive. Pop releases details and returns to the original screen. Replace does not retain the removed branch or its WidgetState.

Why InitState: Navigator is created once per mounted NavigationDemo. Constructing it in Build would reset history. WidgetState owns the controllers; hosts attach and release their tree on unmount. Navigator itself has no Dispose method.

Why an empty OverlayController: no dialogs open yet, but BackNavigation accepts both controllers and checks the top overlay first. Matching NavigatorHost, OverlayHost and BackNavigation are shown. The explicit back button calls Pop; automatic Escape handling requires focus inside this UI.

Push is not a menu-tab switch.

Pushing on each tab press grows history indefinitely. For sections without history, store the selection in State; to replace a route, use Replace.

project-1 identifies a route and must be unique among simultaneously open routes. Pushing the same key twice without popping is invalid. NavigationSnapshot is in-memory history, not automatic persistence after quitting an APK.

The complete example is above; the following blocks are reference fragments. Short snippets below illustrate individual APIs, not complete files. Names such as DashboardPage, ProjectDetails and Location stand for application pages/models, not built-in LumaFlow types.

Mount the scopes once.

Construct controllers at an application boundary and pass them into their matching hosts. The overlay host wraps ordinary content so temporary entries remain scoped to that area.

ApplicationFlow.cs
private readonly Navigator _navigator = new(new DashboardPage());
private readonly OverlayController _overlay = new();

new BackNavigation(
  new OverlayHost(new NavigatorHost(_navigator), _overlay),
  _navigator, _overlay);

Use keys where route identity matters.

Push retains the previous route and its local state. Replace is the right choice when history is no longer useful.

ApplicationFlow.cs
_navigator.Push(new Route(
  new WidgetKey($"project:{project.Id}"),
  new ProjectDetails(project),
  RouteTransition.Fade(TimeSpan.FromMilliseconds(180))));

Let the top overlay own input.

Modals block the content below them. Keep required decisions non-dismissible and close through the returned handle or the dialog's action.

DeleteProject.cs
_overlay.ShowModal(
  new Dialog(new Text("Delete this project?")),
  new ModalOptions(
    dismissOnBarrier: false,
    dismissOnBack: false));

Escape closes the topmost scope first.

BackNavigation resolves input in order: the top overlay, the active route, then nothing at the root. This prevents a required dialog from leaking Escape to the route underneath it.

Keep history bounded.

Inactive routes remain mounted to preserve local state. Use Replace, PopToRoot or ClearAndPush for flows that do not need a full back stack.
