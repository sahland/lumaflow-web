Guide / Controls and forms

Keep the value outside the control that edits it.

LumaFlow inputs are controlled by explicit state. Native UI Toolkit handles focus, keyboard input and accessibility while your application owns the value.

Input rule

State firstInput commits the owned value before invoking its change callback.

A complete form: edit → validate → save → cancel.

Use AppRoot and the theme from the first tutorial. Add ProjectFormDemo.cs below and using LumaFlowDocs.NextSteps; to AppRoot. Replace CounterPage with new ProjectFormDemo() inside the existing Scaffold. Keep Bootstrap unchanged; this is not a GameObject component.

“Save locally” saves only in this screen's memory.

This example does not write files, make requests or send emails. The checkbox is a sample setting. Quitting or removing this branch discards saved values. A real persistence service is a separate concern.

ProjectFormDemo.cs · complete file
#nullable enable
using LumaFlow;

namespace LumaFlowDocs.NextSteps {
    public sealed class ProjectFormDemo : StatefulWidget<ProjectFormDemoState> { }

    public sealed class ProjectFormDemoState : WidgetState {
        private readonly State<string> _name = new("");
        private readonly State<bool> _updates = new(false);
        private readonly State<string> _status = new("Not saved");
        private readonly State<int> _userChanges = new(0);
        private readonly FormState _form = new(FormValidationMode.OnSubmit);
        private FormField<string> _nameField = null!;
        private string _savedName = "";
        private bool _savedUpdates;

        protected override void InitState() {
            _nameField = new FormField<string>(_name, value =>
                value.Trim().Length >= 3 ? null : "Use at least 3 characters.");
        }

        public override Widget Build(BuildContext context) => new ScrollView(new Center(
            ConstrainedBox.AtMost(new Padding(
                new Form(_form, new Column(new Widget[] {
                    new Text("Project settings", context.Theme!.Typography.Title),
                    new TextField(_nameField, label: "Project name",
                        placeholder: "Enter a name", onChanged: _ => UserEdited()),
                    new Checkbox(_updates, label: "Email updates",
                        onChanged: _ => UserEdited()),
                    new Button("Save locally", () => { _form.Submit(SaveValidated); }),
                    new Button("Load example", LoadExample),
                    new Button("Restore saved", RestoreSaved),
                    new ReactiveBuilder<string>(_status, value => new Text(value)),
                    new ReactiveBuilder<int>(_userChanges,
                        value => new Text($"User changes: {value}"))
                }, gap: 16f), onSubmit: SaveValidated),
                EdgeInsets.All(24f)), width: 520f)));

        private void UserEdited() {
            _userChanges.Value++;
            _status.Value = "Unsaved changes";
        }

        // Form.Submit invokes this only after mounted fields pass validation.
        private void SaveValidated() {
            _savedName = _name.Value.Trim();
            _savedUpdates = _updates.Value;
            _status.Value = $"Saved locally: {_savedName}";
        }

        private void LoadExample() {
            _name.Value = "Demo project";
            _updates.Value = true;
            _form.ClearValidation();
            _status.Value = "Example loaded (not saved)";
        }

        private void RestoreSaved() {
            _name.Value = _savedName;
            _updates.Value = _savedUpdates;
            _form.ClearValidation();
            _status.Value = "Restored last saved values";
        }
    }
}

Test the workflow

  1. Press Save locally immediately. Expect Use at least 3 characters. and focus on the name field. Invalid values are not saved.
  2. Enter “My project”, enable Email updates and press Save locally. User changes counts user actions; the status becomes Saved locally: My project.
  3. Press Load example. The name becomes Demo project, the checkbox becomes checked and the status says the example is not saved. User changes does not increase: code assigned those values.
  4. Press Restore saved. The last successfully saved name and checkbox return, not Demo project. Before the first save, this restores an empty name and unchecked box.
  5. Enter a valid name and press Enter in the single-line input: it follows the same save path. In a multiline TextField, Enter inserts a line rather than submitting.

Why three different objects?

Value, field and form
ObjectResponsibility
State<string> _nameThe current draft edited by TextField.
FormField<string> _nameFieldA reference to the same State, its validator and ErrorText; not another name value.
FormState _form + FormValidation of mounted registered inputs, submission and first-invalid focus.

FormField registers through its mounted TextField; constructing the objects alone is insufficient. The input must be inside Form. A validator returns an error string or null for success; do not perform network calls or mutate other state in it.

Why do the button and Enter call different methods?

The button calls _form.Submit(SaveValidated): validate first, then act. In Form(..., onSubmit: SaveValidated), Form already validates Enter submissions. SaveValidated neither validates again nor runs during Build.

OnSubmit reveals errors after a submission attempt. Use FormValidationMode.OnChange to validate with visible errors on value changes instead. FormState.IsValid tracks validity before submit, but does not imply error messages are already displayed.

User callbacks versus code-driven changes

TextField/Checkbox commit State before calling onChanged. Assigning _name.Value = "Demo project" refreshes the native control without replaying onChanged. Load example and Restore saved therefore set their own status explicitly. For logic that must run on every State change, Subscribe in an owner and dispose that subscription; do not treat onChanged as a universal loading callback.

What does resetting a form mean?

ClearValidation clears messages, not values or validity. RestoreSaved first restores both values, then clears errors. _savedName/_savedUpdates intentionally hold the last confirmed version, not a competing source of the current draft.

Common mistakes

Constructing FormField in Build loses stable ownership and messages. Submitting without Form, or with inputs outside its scope, cannot validate those missing inputs. Rebuild is not a data reset. Saving in onChanged runs on every user change, not only the Save button.

When saving becomes asynchronous

This example is synchronous. Networking needs a saving state, duplicate-submit prevention, failure handling and cancellation when the screen goes away. Do not show success before the server confirms. Apply background results on Unity's thread and do not update an unmounted branch. Inject network services instead of creating them in Build.

One state value, one source of truth.

Programmatic changes refresh the control without replaying the user callback. This keeps validation and domain updates in one predictable direction.

ProjectForm.cs
private readonly State<string> _name = new("");

new TextField(
  _name,
  label: "Project name",
  placeholder: "Enter a name",
  onChanged: value => SaveDraft(value));

Model validation as owned form state.

Keep validation close to the field or form owner. Submit only after the form has validated its fields; error presentation remains part of the control contract.

Do not rebuild a form to reset it.

Reset owned field values deliberately. Rebuilding a widget tree is not a substitute for deciding what application data should change.

Style controls through a theme, then override with intent.

ThemeData supplies component defaults. A local style can override only the values it needs while retaining the rest of the active theme.

new Theme(
  theme,
  new Button("Save project", Save, ButtonVariant.Primary));
